# Autopilot procedures

Scheduled runs start fresh with no memory. Read `CLAUDE.md`, `VISION.md`, `ART_DIRECTION.md`, `.autopilot/state.json`, and `BACKLOG.md` first.

## Ticket types
- `(code)` (the default, untagged): one small change, about 30 to 50 changed lines.
- `(model)`: build one 3D model that the vision needs. Follows the Model workflow below. Exempt from the line limit for the script and GLB, but held to `ART_DIRECTION.md`.
A model ticket counts as one commit. Do at most THREE model tickets per daily run (a failed attempt counts).

## Reviewers
Reviews are done by separate subagents with fresh context. Each gets ONLY its rubric file, the ticket text, and its inputs. Never give them your own reasoning or a prior verdict.
- **Code critic** (`.autopilot/reviewers/code-critic.md`): input is the ticket and `git diff`. Always used.
- **Artist critic** (`.autopilot/reviewers/artist-critic.md`): input is the ticket and screenshots. Used whenever a change touches how something looks (not for pure text or data swaps), and always for `(model)` tickets. For `(code)` tickets it runs in **change mode**: it gets `before.png` and `latest.png`, judges only what the ticket changed, and approves if that change is good and the scene is not worse. Whole-scene scoring is for `(model)` tickets and the weekly visual review.
Run the reviewers on Sonnet. On REJECT, allow one revision and re-review. If the critic's fixes are about things the ticket did not touch, do not revise; re-review once with a reminder to stay in change mode. A second reject means revert and mark the ticket `[!]` with the critic's notes. Exception: `(model)` tickets and tickets that add a new visual object get the revisions allowed by the Model workflow (up to 8 critic passes with an early stop), and the builder does the self-check from the Model workflow (look at its own previews and fix obvious problems) before the first critic review.

## Screenshots
Needs playwright: `npm i --no-save playwright` (do not commit it). `tools/shot.mjs` uses the system Chrome at `/opt/google/chrome/chrome` if present, because the sandbox blocks Playwright's own browser download.
1. `npm run build`, then `npm start &`, then wait until `http://localhost:3000` responds.
2. `node tools/shot.mjs http://localhost:3000 .autopilot/shots/latest.png`
3. Stop the server when finished. Screenshots in `.autopilot/shots/` are never committed.
If screenshots cannot be taken, say so in the log and fall back to the code critic only, but do not approve model tickets without preview images.

## Build run (nightly, with a weekly random plan)
One recurring scheduled task starts this run every night at about 9:28 PM ET, including weekends. Most nights it should do real work only on planned days. The randomness lives here, in the weekly plan stored in `.autopilot/state.json`: 4 to 7 random days per week (weekends included), 1 to 10 commits per planned day. A long run may pass midnight. `D` always means the America/New_York date when the run STARTED, even after midnight.
1. If `PAUSE` exists in the repo root, stop. Write nothing, commit nothing, push nothing.
2. `git pull origin main`. Set git author as in `CLAUDE.md`.
3. Read `.autopilot/state.json`.
   - Let `M` be the Monday of the week containing `D`. If `week_start` is not `M`, roll a new plan for the week IN MEMORY ONLY: use `python3` with `random.Random(f"portfolio-{M}")` (seeded by the Monday date, so every night of that week rolls the identical plan), pick `k` as a random integer from 4 to 7, choose `k` distinct dates from `M` through that Sunday that are not before `D`, and give each a random integer of commits from 1 to 10. Do not write or commit it yet. It is saved to `state.json` (`week_start = M`, `week_commits = 0`, `plan = [{date, commits, status: "pending", made: 0}, ...]`) inside the first real commit of the week. Never edit the plan again except to update `status` and `made`.
   - Find the plan entry whose `date` is `D`. If there is none, or its `status` is not `pending`, STOP SILENTLY. Zero planned commits means zero commits: write no log entry, change no file, make no commit, push nothing. Do not install packages or run anything else.
   - `allowed = min(entry.commits, weekly_cap - week_commits)`. If `allowed <= 0`, stop silently the same way.
   - Do not START a new commit after 2:00 AM ET. If time runs out, stop and log how many were left.
4. Repeat `allowed` times:
   a. Tickets under `## Priority` in `BACKLOG.md` come first, in order, whatever the theme. Skip any ticket whose text says `(Needs: X)` until a done ticket provides X. Otherwise take the top unchecked ticket in `BACKLOG.md` that matches the "Current theme" line, or the top unchecked ticket if none match. Skip `(model)` tickets after the third one this run. If no unchecked tickets remain, write 6 new small tickets from `VISION.md` first (commit as `docs: refill backlog`), then continue. Mark the ticket `[~]` while working.
   b. For rendered tickets, first take a baseline shot to `.autopilot/shots/before.png`. Implement only that ticket. For `(model)` tickets, follow the Model workflow.
   c. For `(code)` tickets, check `git diff --shortstat`. If over about 60 changed lines (excluding lockfiles and `.glb`), revert with `git checkout -- . && git clean -fd`, split the ticket into smaller tickets in `BACKLOG.md`, and continue.
   d. Run `npm run check`. On failure, try one fix. If it still fails, revert, mark the ticket `[!]` with a one-line reason, and continue.
   e. If the change touches anything rendered (`src/components`, `src/app`, `public/models`, palette, styles), take a screenshot (see Screenshots). When a model or object is placed or changed in the scene, also run `node tools/scene-crop.mjs .autopilot/shots/after <port> [fx fy fw fh]` (and `before` first) and give the artist critic the desktop, mobile and crop images, since the preview does not show real size.
   f. Run the reviewers (see Reviewers). The artist critic also gets the screenshot.
   g. On approval, mark the ticket `[x]`, commit (format in `CLAUDE.md`), `git push origin main`, and update `state.json` (`week_commits`, and the plan entry's `made`).
   h. Deploy check: poll `gh api repos/Eab0u/Portfolio-Website-V2/commits/<sha>/status --jq .state` every 20 seconds for up to 5 minutes. If it becomes `failure` or `error`, run `git revert --no-edit <sha>`, push the revert, mark the ticket `[!]` with "deploy failed", log it, and STOP for the day. If it is still `pending` after 5 minutes, log that and continue.
5. Set the plan entry's `status` to `done` (or `partial` if you stopped early) and `made` to the number of commits. Append a short entry to `.autopilot/log.md`: date, planned N, commits made, tickets skipped, deploy results, and any rate-limit stop. Fold the log and state updates into the LAST real commit of the run (amend it before pushing; they do not count toward the line limit). Never make a separate bookkeeping commit, so commits made always equals the plan.
6. Stop immediately on any rate-limit or usage error. Log it and mark the entry `partial`. Do not try to catch up on another day.

## Model workflow (for `(model)` tickets)
Builder and critic loop (models only; `(code)` tickets stay on Sonnet):
- **Builder = Opus subagent** (Agent tool with `model: "opus"`). Give it the ticket, `ART_DIRECTION.md`, the palette, `tools/models/README.md`, every earlier critic note on that ticket, and the preview URL and shot command. It writes the generator, runs it, renders the 4 previews as `.autopilot/shots/<name>/roundN-angleK.png`, does the self-check (step 4), and reports the final round and image paths. It never commits.
- **Critic = fresh Sonnet subagent each pass.** Give it only the rubric (`.autopilot/reviewers/artist-critic.md`, Full mode), `ART_DIRECTION.md`, `benchmarks/BRIEF.md`, the ticket text, the 4 lit image paths plus the extra inputs listed below, and a note to ignore the small Next dev badge. Never give it the builder's reasoning.
- **On REJECT:** first reconcile. Compare the new fixes with the previous round's fixes. If one asks for the opposite of an earlier one, follow the newest note unless it would undo a fix the critic already accepted, and tell the builder which notes to ignore and why. Then resume the same Opus builder with SendMessage and paste the decision, scores, and the reconciled fixes. If it cannot be resumed, start a new Opus builder with the notes. Then run a fresh critic again. Up to 8 critic passes in total, but stop early if, after pass 4 or later, the best average of the last 3 passes is less than 0.10 above the best average before them: then end the attempt, keep the best round in `.autopilot/wip/<name>/`, and log why.
- **Keep the best round.** Track the average score of each pass. If a revision scores lower than the best earlier round, tell the builder to go back to that round's generator state (keep a copy per round in `.autopilot/shots/<name>/roundN/`) and revise from there.
- **Critic inputs also include:** the ledger (below) and the previous pass's scores, the unlit albedo images for angles 0 and 2 (`roundN-angle0-unlit.png`, labelled palette only) with the `model-check` output, the approved references in `.autopilot/reference/` (island, crystals, palm, pine, plus the unlit palm) as a known 7 or 8, and the real hero scene (`hero-desktop.png`, `hero-mobile.png`) so it judges scale. If a color looks wrong lit but fine unlit, the fix is lighting or emissive, not the palette.
- **Numbers before critics.** Every builder round runs `node tools/model-check.mjs <name> roundN` (needs the preview server; it renders lit and unlit images and prints frame size, shadow saturation, grey share, lighting hue drift, pink shift, shadow to light value, satKept, greyMid and a per-surface unlit to lit table). Fix every `FAIL` line before reporting, or say in the report why one is acceptable. Build shadow and light colors with `ramp()` from `tools/models/lib/shade.mjs`; never hand-pick shadow hexes.
- **Ledger.** Keep `.autopilot/shots/<name>/ledger.md` with LOCKED (decisions the critic accepted or praised, with IDs L1, L2) and OPEN (issues with IDs F1, F2 and a status). Give it to the builder and to every critic. The critic judges only the OPEN issues and regressions, asks for at most 3 fixes, and may change a LOCKED item only by writing `UNLOCK Ln: reason`. Reconcile only covers notes that are not in the ledger.
- **Audit first, then fix everything.** On pass 1 the critic writes an AUDIT (use the per-surface table from `model-check`): every surface that covers about 5% or more of the visible model, with its unlit color, its lit color, and OK or BAD. Every BAD item goes into the ledger as an OPEN issue (the orchestrator assigns the F-IDs), so the builder fixes them all in one round instead of three per pass. Later passes only update statuses and add genuinely new issues.
- **When all scores are 7 or higher but the average is under 7.5,** the critic adds UPGRADES: the three cheapest moves that would lift one dimension from 7 to 8 (richer silhouette, a stronger focal detail, more facet contrast). These are improvements, not defects. The builder does the upgrades plus any open issues. Fixing defects alone plateaus at 7.0.
- **Lighting problems are fixed in the material.** If `model-check` or the critic shows a surface that is fine unlit but dull, grey or shifted lit, follow the Lighting section of `tools/models/README.md` (soft emissive tint in its own mesh, pre-compensated hue). Do not ask to change the preview lights: they match the real scene on purpose.
- **Compute the average yourself** from the six scores. REJECT if it is under 7.5 or any score is under 7, whatever the critic wrote.
- **Persist the best round.** When a model attempt ends rejected, copy the best round's generator folder and GLB to `.autopilot/wip/<name>/` and include it in the day's last commit (bookkeeping, outside the line limit). A retry copies it back first and continues from it. Delete the folder when the model is approved.
- **One subject per model file.** A ticket builds one tree, one prop or one building, in its own GLB, so the preview can frame it large. Do not put a row of different models in one file.
- **Log it.** The log entry for every model attempt must name the builder model that actually ran (opus or sonnet) and list the scores of every critic pass.
- **Opus unavailable or erroring:** fall back to Sonnet and say so in the log.
- **Preview server:** start `npm run dev -- -p 3100` in the background once per run and let the builder use it. Before `npm run check`, stop it, run `git checkout -- next-env.d.ts`, and delete `AGENTS.md` (the dev server creates both).
- **Files:** every generator file must be under 200 lines, so split the script into `tools/models/<name>/*.mjs` modules with a short entry file. Import the shared helpers from `tools/models/lib/` (rng, palette, soup, export) instead of copying them; add new generic helpers there. Re-run it and confirm the GLB hash is identical after any split.
- **Commit** only after the artist critic and the code critic both APPROVE and `npm run check` passes.

1. Read `ART_DIRECTION.md`. Write a short generator script in `tools/blender/` (Blender Python, headless) or `tools/models/` (Node), building the model from named parts using only palette colors.
2. Run it and export a Draco-compressed GLB to `public/models/`. Check the size (under 500 KB) and triangle count (within the budget in `ART_DIRECTION.md`). If headless Blender is not available, generate the geometry with Node or procedural Three.js instead. Do not block on it.
3. Make sure `/dev/model-preview` exists (see backlog). Take 4 screenshots with `?src=/models/<file>.glb&angle=0..3`.
4. Self-check first: open the 4 preview images (and the `model-check` output) yourself and compare them with `ART_DIRECTION.md`. Fix obvious problems (colors off the palette, hidden or clipped parts, flat or empty areas, a plain base, detail at only one scale) and re-render. Repeat up to 4 times, then hand the 4 images to the artist critic and the script to the code critic (see the loop above). Up to 8 critic passes (see the Builder and critic loop for the early stop). If it still fails, mark `[!]` with the notes and move on. A model ticket that has been rejected in two different runs stays `[!]` and is only reset by the weekly review, after the cause is fixed. If the critic's complaints are about color, check that the preview lighting is neutral before blaming the model.
5. Commit the script and GLB together.

## Weekly code review (Sunday 7:34 PM ET)
Use the code critic mindset (`.autopilot/reviewers/code-critic.md`) on the whole repo, with fresh context. Look at structure, dead code, bundle size, performance of the 3D scene, accessibility, and adherence to `CLAUDE.md`. Write findings to `reviews/YYYY-MM-DD-code.md` (max 1 page). Add up to 8 small, concrete tickets to the top of `BACKLOG.md`. Do not change source code.

Then plan next week. Read `VISION.md`, pick the theme (a district or interest) for the coming week, rotating through the interests and favoring unfinished districts. Update the "Current theme" line at the top of `BACKLOG.md` and write 6 to 8 original, small tickets for that theme at the top, including 1 or 2 `(model)` tickets. Make them specific and visible. Flag any filler commits from the past week in the review. Also compare this week's `plan` in `.autopilot/state.json` with what happened (check `.autopilot/log.md` and `git log`) and flag any planned day that was missed or partial at the top.

Then tidy the backlog: (1) merge duplicate tickets and drop stale or already-done ones; (2) move every `[x]` ticket out of `BACKLOG.md` into `BACKLOG-DONE.md` (create it if missing, append under a dated heading, keep the section name beside each ticket); (3) keep fewer than 300 open tickets. If a new ticket would pass that, merge or drop an old one first. Do not touch tickets under `## Priority` that are still open.

## Weekly visual review (Sunday 8:32 PM ET)
Act as the artist critic (`.autopilot/reviewers/artist-critic.md`) on the whole site. Run the site locally and take screenshots (see Screenshots), including `/timeline` and any other routes. Judge against `benchmarks/BRIEF.md`, `VISION.md`, and `ART_DIRECTION.md`. Score 1 to 10 on: intro ritual, sense of a world, interaction delight, UI restraint, polish and performance, and low-poly consistency. Check that no brand logos or copied assets slipped in. Write `reviews/YYYY-MM-DD-visual.md` (max 1 page) and add up to 8 small tickets to the top of `BACKLOG.md`. Do not change source code.

## Adjusting speed
Edit `weekly_cap` in `.autopilot/state.json` to cap how many commits a week can make. The days per week and commits per day are in the Build run section above and in `rules` in `state.json`.
